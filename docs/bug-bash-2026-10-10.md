### BB-001: duplicate `link.onUpdate` entries from a clock-based link version
**Location:** `packages/worker` link push / `__receiveLinkUpdate`
**Expected:** one `link.onUpdate` on the subscriber per change of the source.
**Actual:** lobby `bb-lobby` has 2 journal events (init, RENAME). auction-room `bb-auction` linked to it has `link.onUpdate` entries 3 (lobby seq 1) and 4 (lobby seq 2), then 9, 10, 12 and 13: four more copies of the same view, all with causationId `lobby/bb-lobby/2`. The link row's `version` is `1791637971861`, a wall-clock timestamp, so a re-push of an unchanged view after the lobby wakes (the in-memory dedupe map is empty after hibernation) passes the monotonic version check. Duplicate history, wasted writes, and a nondeterministic value in the journal path (against ADR-015).
**Also seen:** `targetType` / `sourceType` is the binding name (`LOBBY`), while causation ids use the actor type (`lobby`).
**Steps:** link auction-room → lobby, rename the lobby, open both in Studio a few times; read `/__studio/api/actors/auction-room/<id>/timeline`.
**Fix direction:** the link version is the source's journal seq.
