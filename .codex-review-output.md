# Binary Wire Protocol

## Overview

Actor Kit v2 replaces JSON Patch with schema-aware binary delta encoding. The `schema()` builder defines the binary layout at compile time. The encoder sends only changed fields using a bitmask. The decoder on the client reconstructs the view.

## Frame format

Every WebSocket frame starts with a 4-byte header:

```
Byte 0: version (uint8) — schema version, used for version negotiation
Byte 1: type (uint8) — frame type
Bytes 2-3: length (uint16, big-endian) — payload length in bytes
```

# ADR 001: Offensive Type Safety

**Date**: 2026-03-22
**Status**: Accepted

## Context

Actor Kit v2's `actor()` function infers types across multiple layers: state from `init()`, roles from `roles` keys, message types per role, view schemas per role, and a discriminated union of all views. If any layer uses `any` or `as` casts, the inference chain breaks and the user loses type safety in their client code.

## Decision

TypeScript's type system is a development accelerator, not a tax. We treat it offensively:

### Rules

1. **No `any`** — use `unknown` and narrow with type guards or Zod parsing.
2. **No `as` casts** — if the compiler can't verify it, restructure until it can. The only acceptable escape hatch is `as const` for literal inference.
3. **No non-null assertions (`!`)** — check for null/undefined explicitly.

The docs currently define several foundational behaviors that cannot be implemented safely as written: client message parsing has no schema carrier, role-specific client typing breaks on runtime role changes, and both the auth and binary reconnect protocols have correctness/security gaps. I would not treat this as a sound implementation blueprint yet.

Full review comments:

- [P1] Add schemas to message definitions — /Users/jonathanmumm/src/actor-kit-2/docs/specs/phase-1-core-runtime.md:80-82
  The `messages` API only accepts bare handlers here, but the rest of the design requires every client message payload to be parsed with Zod before the handler runs. With only `ADD_TODO: (state, { text }) => …`, there is nowhere to attach the runtime schema, so any non-trivial message payload will either bypass boundary parsing or force an untyped side channel to recover the schema. This needs to be specified as a `{ schema, handler }` shape or equivalent before the core API can satisfy its own validation/type-safety guarantees.

- [P1] Stop specializing `ActorConnection` to the first role — /Users/jonathanmumm/src/actor-kit-2/docs/specs/phase-3-client-sdk.md:31-33
  `connect()` makes `send()` and `trigger` depend on the role from the first snapshot, but the same spec later requires handling `ROLE_CHANGED` during reconnects. Once user code holds `const todo = await connect(...)`, that object's generic `TMessages` is fixed, so a mid-session promotion/demotion leaves the client falsely typed for the old permissions or forces an unsafe cast to “re-type” it. The connection surface needs either the union of all messages or a new typed object when the role changes.

- [P1] Stop sending browser JWTs in the WebSocket URL — /Users/jonathanmumm/src/actor-kit-2/docs/specs/phase-3-client-sdk.md:29-29
  In browsers, `WebSocket` does not allow setting an `Authorization` header, so this requirement falls back to query parameters for every real client. That puts bearer JWTs into URLs, proxy/access logs, and error telemetry, which makes token replay possible outside the app boundary. The transport needs a non-URL auth channel such as `Sec-WebSocket-Protocol`, cookies, or an authenticated HTTP upgrade.

- [P1] Require schema parsing for RPC payloads — /Users/jonathanmumm/src/actor-kit-2/docs/specs/phase-5-cf-integration.md:80-85
  ADR 002 explicitly treats DO RPC as a trust boundary, but this spec makes the RPC payload schema “optional”. That means any malformed or buggy actor-to-actor call can reach privileged handlers unparsed, which is the one place the framework would violate its own parse-at-the-boundary rule. RPC payload schemas need to be required and applied with the same safe-parse flow as client messages.

- [P2] Widen the frame length field or define fragmentation — /Users/jonathanmumm/src/actor-kit-2/docs/binary-protocol.md:12-15
  The wire format caps every payload at 65,535 bytes by encoding the frame length as `uint16`, while snapshots and changed arrays are sent in full and strings are also 16-bit length-prefixed. A moderately large first snapshot (for example, a list view with a few hundred longer strings) becomes unencodable even though WebSocket itself supports larger frames. The format needs either a wider length field or explicit fragmentation rules before large views can work.

- [P1] Store prior views, not only checksums, for reconnect deltas — /Users/jonathanmumm/src/actor-kit-2/docs/specs/phase-2-binary-sync.md:89-91
  The reconnect design says the server keeps the last N checksums and, when a client presents one of them, sends a delta “from that point”. A checksum alone is not enough to build that delta—you also need the corresponding prior view (or an append-only patch log) associated with that checksum. As written, reconnect-after-disconnect cannot actually produce a delta once the actor has advanced past the client's snapshot.
